# Design

## Context

- 标签:更新路由 `POST /tags/:id`(name+color)与删除路由已存在,**无重名防护**(直接 UPDATE,撞 UNIQUE(ledger_id,name) 会抛 500);tags.ejs 只有创建表单与删除 ✕,无编辑入口。
- 分类:更新路由 `POST /categories/:id`(name/icon/color)存在但 `is_system=1` 被拦截;删除路由对 is_system 拦截、对引用>0 的分类走归档(is_archived=1,选择列表已过滤归档项)、未引用硬删且父分类连带删子;categories.ejs 无任何编辑 UI,删除 ✕ 仅出现在账本自有二级分类上。
- 系统分类 seed 到 `ledger_id = NULL` 且 `is_system = 1`,跨账本共享。

## Goals / Non-Goals

**Goals:**
- 管理页内完成标签与分类的全量维护(改/删),系统分类解锁。
- 删除语义统一:引用>0 → 归档,未引用 → 硬删。

**Non-Goals:**
- 不做分类移动(改父级/改收支类型)——现有需求只涉及名称/图标/颜色/删除。
- 不做 copy-on-write(把系统分类复制成账本私有副本)——单用户自托管,全局编辑可接受。
- 不改报表/统计对归档分类的展示逻辑(历史保留现状)。

## Decisions

### D1 系统分类解锁,全局生效
移除分类更新/删除路由中的 `is_system` 拦截。系统分类 `ledger_id = NULL` 全局共享,改名/图标/颜色对所有账本生效——单用户自托管场景下这正是用户想要的(「把内置分类改成自己的叫法」)。
**备选**:copy-on-write(编辑时复制为账本私有副本)——查询/统计合并逻辑复杂化,放弃。

### D2 删除语义:有数据一律拒绝(用户澄清,替代原「归档」方案)
- 分类:统计自身与全部子分类的交易引用数(含已删除交易的引用?沿用现有口径 `COUNT(*) FROM transactions WHERE category_id = ?`,含已删除交易——数据仍在库里,删分类会留下悬空引用,故按库内引用计),> 0 → 拒绝删除,flash「该分类下有 N 笔交易,不能删除」;= 0 → 硬删,一级分类连带子分类(沿用 `DELETE WHERE parent_id = ?`)。
- 标签:`COUNT(*) FROM transaction_tags WHERE tag_id = ?` > 0 → 拒绝并提示数量;= 0 → 删除。
- 不再提供「引用>0 归档」的替代路径(用户明确要求有数据不能删除);现有归档数据不受影响,选择列表过滤逻辑保留。

### D3 标签重命名防护
`POST /tags/:id` 更新前检查同账本同名(排除自身):冲突 → flash「标签已存在」不覆盖;正常 → UPDATE。

### D4 编辑 UI:内联展开小表单
- 标签:chip 内加「编辑」按钮,切换内联表单(名称 input + 颜色 color + 保存),仿 accounts.ejs 的 `.acc-edit-form` 展开模式。
- 分类:一级行与二级 chip 均加「编辑」「删除」;编辑表单(名称/图标/颜色 + 保存,kind 与父级不变)展开在分类行内;删除按 D2 由服务端决定归档或硬删,flash 反馈。
- categories.ejs 顶部提示文案同步改为「内置分类也可修改与删除(改名为全局生效)」。

## Risks / Trade-offs

- [系统分类改名影响所有账本] → 单用户自托管可接受;文案注明「全局生效」。
- [重命名撞 UNIQUE 异常] → D3 前置检查避免 500。
- [删除引用计数含已删除交易,偏保守] → 防止软删除记录的分类引用悬空;用户可先批量删除/改分类后再删分类。

## Migration Plan

纯代码与视图改动,无数据迁移;远端同步重建容器即可。
